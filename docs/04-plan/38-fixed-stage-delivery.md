# 整体开发顺序与固定阶段交付规则

日期：2026-10-09。此文取代此前频繁小步派单的协作方式。

## 用户需求与职责

当前第一优先级是完成 PDF 解析及其实际入库、检索、引用能力。长期目标是支持不同
文件格式和内容类型，同时保留可追溯的结构化内容；不能把所有内容压成一个字符串。

- 协调者 `/root`：需求、整体架构、阶段计划、与审核者商讨、交付后的集中完整验收。
- 唯一开发者 `/root/developer_61`：gpt-6.1-sol，medium；实现阶段内全部源码、测试、
  部署脚本和使用文档，自主完成调试与自检。旧 `/root/developer` 已停止。
- 唯一审核者 `/root/design_advisor`：阶段派发前审设计，交付后审集中发现与修改方案。
- 不再创建其他开发或审核 agent。开发阶段不逐文件轮询、不持续插单、不提前逐条审初稿。
- 正常交互只有：整阶段任务书、开发交付报告、集中修改任务书。真正阻断、需求冲突、
  不可逆操作或必须改变已批准架构时，开发者可以提交一份集中问题说明。

## 阶段顺序

| 阶段 | 目标 | 交付边界 | 启动条件 |
| --- | --- | --- | --- |
| P1 当前 | PDF 结构保真与完整链路 | 最小自有 IR、隔离质量解析器、版本化复用、OCR 恢复、只读检查界面、完整验证报告 | 本阶段方案审核通过 |
| P2 | Office/文本适配到同一 IR | DOCX/PPTX/XLSX 原生结构、Excel 公式和缓存值状态、单元格定位；复用既有解析器 | P1 工程与既定PDF质量门槛通过，或用户明确重新排序；另写详细任务书 |
| P3 | 内容增强与结构化查询 | 按需图片/图表理解、受限表格查询、可追溯派生信息；不信任模型估算为事实 | P2 通过；另审成本/权限/模型方案 |
| P4 | 配额与来源导入 | 既有已审配额、归档、爬取计划逐阶段实现 | PDF 优先任务不再阻塞；用户顺序有变化则服从用户 |
| P5 | 评估和生产完善 | 黄金集、可解释比较、部署/备份恢复/性能验收、剩余模块 | 前置能力及具体阶段计划具备 |

P2–P5 是路线图，不是本次开发授权包。P1 期间不穿插 SDK、配额、爬虫或通用 Agent 平台。
此前 SDK 已接受；配额仅有未集成 ORM 草稿，保留但不继续。

## 不变的架构

保留 PostgreSQL、Qdrant、ObjectStore（本地/S3，MinIO 是一种部署）、现有持久任务管线、
控制/数据平面分离。文件格式选择 Parser；项目自有 IR 表达内容；类型处理产生可追溯
派生表示；现有 chunker/indexer/retriever 消费派生表示与原始引用。

Docling 是解析适配器，不是公共业务 Schema。Markdown/search_text/向量是派生产物。
原始文件、版本化 IR、模型/解析来源、结构化内容和资产共同支持追溯；机器提取结果不因
存进 JSON 就被认定为真实无误。父子 chunk 不替代 element 身份或完整原始表格。

## 完整交付和验收

开发者在一个阶段内完成所有工作包及自检后，只提交一份交付报告，包含变更清单、
需求对应表、测试命令/结果/跳过原因、固定源码与模型身份、真实样本报告、运行方法和
已知限制。源码自检通过后冻结交付版本；验收期间不继续改同一组文件。

root 按阶段验收矩阵统一执行：源码/架构检查、自动测试、真实服务、界面和样本质量。
先完成一轮矩阵再向开发者反馈，除非发现会损坏数据或导致后续验收不可信的严重阻断。

发现集中记录在同一份报告：编号、需求、严重度、复现、预期/实际、证据、根因假设、
影响范围、修复建议、必须补测。root 与原审核者确认后形成一份明确修改任务书，再整批
交开发者；不要边讨论边同时修改。补丁交付后重跑受影响矩阵及必要回归。

工程验收和质量门槛分别记账。没有独立标注、未跑性能测试或质量分数未达标时，不能
写“PDF 全部完成”。可以完成工程交付并继续同一 PDF 任务处理质量问题，但不可把未达
门槛从清单删除，也不可用成功解析数量代替质量。

## 工作区与环境

保留所有既有 dirty work。未授权 commit/push/包发布/公司环境同步。docs/tests 的现有
全局忽略规则不变，不强制添加。只启动一个完整产品栈；测试数据库只能使用专用临时
服务，禁止向产品数据执行 TRUNCATE。日志不得输出密钥。阶段内实现者独占集成测试
数据库，集中验收时明确移交给 root。
